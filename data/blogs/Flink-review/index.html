00 一页看懂整条链路

核心问题：订单不断产生，但可能乱序或迟到。Flink 怎么实时、尽可能准确地统计每 10 秒的 GMV？

一句话：CDC 负责「感知变化」，Window 负责「按时间分组」，Watermark 负责「推进事件时间、触发窗口」，Allowed Lateness 负责「有限补算」，Side Output 负责「分流特殊数据」。

01 先记住业务指标：PV / UV / GMV

PV · Page View

页面浏览次数
18

3 人分别浏览 10、5、3 次 → PV = 18。

UV · Unique Visitor

独立访客数
3

同样的 3 个人 → UV = 3（按某个统计周期去重）。

指标通俗理解注意
PV页面被看了几次一个人可以产生多次 PV
UV来了几个不同访客依赖用户 / 设备识别和统计周期
加购把商品放进购物车可能统计人数，也可能统计次数
购买下单或支付成功必须明确业务口径
GMV商品交易总额不等于利润；退款处理看口径
转化漏斗浏览 → 加购 → 购买用来找出流失环节
快速区分：PV 是「次数」，UV 是「人数」。如果 1000 人来店铺、50 人购买，按购买人数统计的访客购买转化率就是 50 ÷ 1000 = 5%。

02 Flink CDC：实时发现数据变化

CDC = Change Data Capture（变更数据捕获）。Flink CDC 常用于把数据库的新增、修改、删除持续同步到其他数据系统。

数据库动作CDC 捕获的变化例子
INSERT新增记录新订单产生
UPDATE更新记录订单从未支付变成已支付
DELETE删除记录订单记录被删除
UPDATE orders
SET status = 'PAID'
WHERE id = 1001;

对于 MySQL，CDC 通常先读取已有数据的快照，再持续读取 Binlog 中的增量变更。

区别：Flink CDC 重点解决「数据库变化怎么被持续读取、同步」；Flink 的流计算负责「如何过滤、分组、聚合、计算」。两者常配合使用。

03 Window：把无限数据按时间分组

订单会不断到来，不可能等所有数据都到齐才统计。Window（窗口）让我们统计某一个时间范围内的数据。

窗口类型特点例子
Tumbling 滚动不重叠、固定大小[0,10)、[10,20)、[20,30)
Sliding 滑动可以重叠，同一数据可能属于多个窗口每 5 秒统计最近 10 秒
Session 会话按一段无活动间隔来划分用户连续操作视为一次会话

这里的 [10,20) 是数学上的左闭右开区间：包括第 10 秒，不包括第 20 秒。

04 Event Time：先区分「发生」和「到达」

订单事件发生时间（Event Time）Flink 收到的时间
A10:00:0110:00:02
B10:00:0410:00:05
C10:00:0310:00:08

C 的发生时间比 B 早，但收到得比 B 晚，这叫乱序到达（Out-of-order）。

Event Time · 事件时间

订单真实发生的时间。事件时间窗口按它来决定归属。

Processing Time · 处理时间

Flink 处理记录时的系统时间。处理时间窗口的行为与事件时间窗口不同。

重要：在 Event Time 滚动窗口中，事件时间是第 8 秒的订单，永远归属于 [0,10) 这个窗口；即使第 25 秒才到，也不会自动改投 [20,30) 窗口。

05 Watermark：告诉 Flink 事件时间推进到哪里了

不能要求数据严格按事件时间到达。Flink 使用 Watermark（水位线）表示事件时间进度，用于触发事件时间定时器和窗口计算。

直觉：Watermark = 20 秒，表示系统认为「事件时间早于大约 20 秒的记录通常应该到得差不多了」，但不是保证不会再来。

常见的有界乱序策略

最大已观察事件时间：25 秒
允许乱序程度：       5 秒
Watermark：          约 20 秒

为便于理解，示例省略毫秒级边界细节；实际 Flink 的有界乱序 Watermark 生成实现通常涉及约 1 毫秒的边界偏移。

事件时间最大值25 秒
−
乱序容忍5 秒
≈
Watermark20 秒

当 Watermark 推进到窗口结束边界附近（更准确地说，达到窗口最大时间戳）时，默认事件时间触发器会让该窗口首次计算。

常见误解：「Watermark 延迟 5 秒」不等于机器收到一条数据后固定等 5 秒。它描述的是基于事件时间的进度滞后。

补充：多分区并行处理时，算子的有效 Watermark 还可能受慢分区影响；Watermark 的推进也依赖生成与传递机制，不一定每条数据都立刻更新。

06 Allowed Lateness：首次出结果后还能补算

窗口首次触发后，可能还有属于它的订单到达。Allowed Lateness（允许迟到）用于让事件时间窗口在额外一段事件时间范围内继续接受晚到记录。

Watermark 延迟

主要目的是推迟首次触发，给乱序数据更多时间到来。

Allowed Lateness

主要目的是首次触发后继续保留窗口，允许晚到数据更新结果。

同一窗口如何从 ¥500 变成 ¥600？

首次输出GMV = ¥500
→
迟到一笔订单+ ¥100
→
再次输出GMV = ¥600
例子：窗口为 [10,20)、Allowed Lateness 为 10 秒。窗口约在 WM 到达 20 秒时首次触发；当 WM 仍未达到约 30 秒的清理界限时，迟到记录通常还能更新它；到达清理界限后则太晚。

注意：这里的「10 秒」是按 Watermark 所表示的事件时间计算，不是现实时间里固定再等 10 秒。具体行为以窗口类型、触发器和 API 为准；此处指常见的 DataStream Event Time 窗口。

07 Side Output：给特殊数据开一条支线

Side Output（侧输出）是在主数据流之外额外输出一条（或多条）流。常用于接收超过允许迟到期限的数据、脏数据、异常事件等。

主输出 · Main Output

正常窗口计算

如 [10,20) GMV

¥1,000

写 Doris / 实时大屏

侧输出 · Side Output

过期迟到订单

事件时间在 17 秒，现已太晚

+ ¥100

写补偿流 / 告警 / 存档

DataStream Java API（示意）

// 为迟到订单准备一个侧输出标签
OutputTag<Order> lateTag =
    new OutputTag<Order>("late-orders") {};

// 假设 orderStream 已设置事件时间戳和 Watermark
SingleOutputStreamOperator<Order> result = orderStream
    .keyBy(order -> order.userId)
    .window(TumblingEventTimeWindows.of(Time.seconds(10)))
    .allowedLateness(Time.seconds(5))
    .sideOutputLateData(lateTag)
    .sum("amount");

// 获取已经超过窗口清理期限的记录
DataStream<Order> lateOrders = result.getSideOutput(lateTag);

这是常见 DataStream API 写法的概念示例；具体 Flink 版本、Order 类型字段、Watermark 配置等需与项目匹配。

注意：Side Output 不会自动补算 GMV，也不会自动落库。只有给侧输出流接上后续处理逻辑，数据才能进一步补偿或保存。若未配置侧输出，过期迟到记录通常会被丢弃。

09 高频易错点（面试很常问）

常见误解正确理解
❌ 迟到订单会被放进下一个窗口✅ 事件时间决定窗口归属，不会因为到达晚就自动改窗口
❌ Watermark = 20，表示 20 秒之前数据绝不再来✅ Watermark 只是时间进度判断，不是绝对保证
❌ Watermark 延迟就是实际睡眠等待 N 秒✅ 它通常是事件时间进度落后最大已观察事件时间 N 秒
❌ Allowed Lateness 是第一次计算之前额外等 N 秒✅ 它主要影响首次触发之后能否继续接受晚到数据
❌ Side Output 只能输出迟到数据✅ 它是通用的分流机制，也能处理脏数据、异常事件
❌ Side Output 会自动修正结果✅ 侧输出只是拿到另一条流；补偿逻辑需要自己写
❌ GMV 就是利润✅ GMV 是交易总额，不等于利润

用同一笔订单串起来

  1. 订单在事件时间 17 秒发生，属于 [10,20)。
  2. Watermark 超过 20 秒附近时，窗口通常已首次输出结果。
  3. 若 Allowed Lateness = 10 秒、WM 仍小于约 30 秒，订单可以进入原窗口，触发补算。
  4. 若 WM 已达到约 30 秒的清理边界，订单已经太晚，可配置进入 Side Output。
  5. 无论迟到多严重，都不会仅因迟到就被转入 [20,30)。

10 最终速记卡：30 秒恢复记忆

Flink CDC感知数据库的 INSERT、UPDATE、DELETE，把变更持续读取出来。
Window把无限数据按时间或会话等规则划分，分别统计。
Event Time事件真正发生的时间，决定它属于哪个事件时间窗口。
Watermark推进事件时间，决定事件时间窗口何时可以触发。
Watermark 乱序容忍让 Watermark 落后观察到的事件时间，给乱序数据留空间。
Allowed Lateness首次输出之后，窗口仍可接收一段范围内的迟到数据并更新。
Side Output主流之外的数据分流，例如过期迟到订单、异常数据。
PV vs UVPV 看页面浏览次数；UV 看独立访客数。
面试一口气答：Flink CDC 抓取数据库变更；事件按 Event Time 进入对应 Window；Watermark 推进事件时间并触发计算；如果窗口首次触发后有迟到数据，Allowed Lateness 决定是否还能修正；超过期限的数据可通过 Side Output 分流处理。
