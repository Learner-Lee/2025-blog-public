## 二、代码库理解与导航

### C01｜梳理数据管线与上下游依赖

- **使用团队**：基础设施团队的新入职数据科学家。
- **工作问题**：不熟悉代码库，需要理解数据管线及仪表盘的数据来源。
- **输入材料**：代码库、相关 `CLAUDE.md` 项目说明文件。
- **操作流程**：读取并识别相关项目说明 → 解释数据管线依赖 → 指出仪表盘所依赖的上游数据源。
- **产出与原文效果**：获得代码和数据依赖解释，帮助新人更快开展工作；原文称这一做法替代了传统数据目录工具的部分使用场景，未报告量化结果。
- **可迁移做法**：接手项目时，先梳理“输入数据 → 处理流程 → 最终输出”的关系，再修改代码。

### C02｜开发前定位相关文件

- **使用团队**：产品工程团队。
- **工作问题**：修复缺陷、开发功能或进行分析前，需要花时间寻找相关代码。
- **输入材料**：代码库、具体任务描述。
- **操作流程**：描述任务 → 请求识别需要检查的文件 → 根据定位结果开展开发或分析。
- **产出与原文效果**：获得相关文件与代码位置，减少手工收集上下文的时间；未报告量化结果。
- **可迁移做法**：让助手先回答“这个问题涉及哪些文件、为什么”，形成后续工作的入口。

## 三、测试与代码审查

### C03｜编写测试并自动处理部分 PR 问题

- **使用团队**：产品设计团队。
- **工作问题**：新功能需要测试，PR 中还包含格式与测试用例重构等重复工作。
- **输入材料**：新功能及相关代码；原文未披露完整 CI 配置。
- **操作流程**：为新功能编写测试；结合 GitHub Actions 自动化处理 PR 评论相关工作，并处理格式问题和测试用例重构。
- **产出与原文效果**：测试代码及部分自动化修改；未报告覆盖率、缺陷率或节省时间。
- **可迁移做法**：把测试编写和可自动处理的审查事项接入已有开发流程，并明确自动处理范围。

### C04｜用伪代码与测试驱动开发推进实现

- **使用团队**：安全工程团队。
- **工作问题**：传统流程容易经历“设计文档 → 粗糙实现 → 重构”，最后放弃补测试。
- **输入材料**：待实现的任务与需求；原文未列出完整输入清单。
- **操作流程**：先请求伪代码 → 引导 Claude 按测试驱动开发方式实现 → 人员定期检查进展。
- **产出与原文效果**：原文称代码变得更可靠、更容易测试，未提供对照数据。
- **可迁移做法**：将实现思路和验收条件前置，避免把测试留到开发末尾。

### C05｜在不熟悉的语言中实现测试

- **使用团队**：推理团队。
- **工作问题**：知道需要验证什么行为，但不熟悉项目所使用的语言，例如 Rust。
- **输入材料**：要测试的功能或行为描述、代码库的语言环境。
- **操作流程**：用自然语言解释测试目标 → Claude 用代码库的原生语言编写测试逻辑。
- **产出与原文效果**：得到目标语言的测试实现；未报告通过率或节省时间。
- **可迁移做法**：由人明确测试语义，让助手承担语法和语言惯例的转换。

## 四、调试与故障排查

### C06｜结合堆栈和文档追踪故障

- **使用团队**：安全工程团队。
- **工作问题**：事故发生时，需要快速理解不熟悉代码的执行路径。
- **输入材料**：堆栈跟踪、相关文档、代码库。
- **操作流程**：提供堆栈与文档 → 沿代码库追踪控制流 → 辅助理解和定位问题。
- **产出与原文效果**：原文称，通常需要手工扫描 10–15 分钟的问题，借助工具后处理速度约提高到 3 倍；未说明样本量或测量方法。
- **可迁移做法**：排障时同时提供错误证据、代码与文档，减少仅凭错误消息推测原因。

### C07｜修复陌生代码库中的缺陷

- **使用团队**：产品工程团队。
- **工作问题**：遇到其他代码库中的缺陷，通常需要向对应工程团队求助。
- **输入材料**：观察到的异常行为、相关代码库。
- **操作流程**：描述异常行为并请求修复 → Claude 提出解决方案 → 工程师审阅方案。
- **产出与原文效果**：获得可供审阅的修复方案，增加跨代码库处理问题的能力；未报告量化结果。
- **可迁移做法**：把具体异常作为入口，通过方案审阅逐步理解陌生模块。

### C08｜排查 Kubernetes Pod 调度故障

- **使用团队**：数据基础设施团队。
- **工作问题**：Kubernetes 集群停止调度 Pod，需要在故障期间快速找出原因。
- **输入材料**：监控仪表盘截图及排查过程中看到的界面信息。
- **操作流程**：提交截图 → 根据 Claude 的逐级菜单指导检查 Google Cloud 界面 → 识别 Pod IP 地址耗尽 → 获得创建新 IP 地址池并加入集群的命令。
- **产出与原文效果**：定位到 IP 地址耗尽，并获得对应处理命令；原文称节省约 20 分钟，未说明对照方式。
- **可迁移做法**：当故障线索分散在图形界面中时，可把截图与逐步观察结果作为诊断上下文。

## 五、原型与功能开发

### C09｜从设计文件进入自主开发循环

- **使用团队**：产品设计团队。
- **工作问题**：需要将设计或抽象需求快速转化为可运行功能。
- **输入材料**：Figma 设计文件，或抽象的问题描述。
- **操作流程**：提供设计或问题 → Claude 编写代码 → 运行测试 → 持续迭代 → 人员审阅方案并做最后调整。
- **产出与原文效果**：得到功能实现；原文另举为 Claude Code 自身构建 Vim 键位绑定的例子，称所需人工审阅较少，未提供统一效率数据。
- **可迁移做法**：将代码修改、测试运行和反馈调整组成循环，同时保留明确的人工验收环节。

### C10｜在设计阶段发现边界情况

- **使用团队**：产品设计团队。
- **工作问题**：错误状态和逻辑遗漏常到开发阶段才暴露，造成返工。
- **输入材料**：待设计的功能或交互；原文未说明具体输入格式。
- **操作流程**：梳理错误状态、逻辑流和系统状态 → 在设计阶段识别边界情况。
- **产出与原文效果**：补充设计中的边界情况；原文称改善初始设计质量，并节省数小时的后续调试时间，未提供测量细节。
- **可迁移做法**：在实现前检查失败分支、状态转换和异常情况，并将发现补入设计或验收条件。

### C11｜跨语言构建强化学习性能可视化

- **使用团队**：不熟悉 TypeScript 的数据科学家。
- **工作问题**：需要展示强化学习模型性能，但缺乏对应前端开发能力。
- **输入材料**：可视化需求提示；原文未披露具体数据结构与完整提示词。
- **操作流程**：在沙盒环境中一次性提出需求 → Claude 从头编写 React／TypeScript 可视化应用 → 若结果不足，略微调整提示后重试。
- **产出与原文效果**：生成完整可视化应用，使用者无需先掌握其全部实现；原文未报告成功率，且将该场景描述为相对简单的任务。
- **可迁移做法**：先明确需要观察的指标和交互，再借助助手构建可运行的可视化原型。

## 六、文档与知识管理

### C12｜理解模型相关函数

- **使用团队**：推理团队中缺乏机器学习背景的成员。
- **工作问题**：需要理解模型相关函数，独立查找资料耗时较长。
- **输入材料**：需要理解的模型相关函数；原文未说明全部上下文来源。
- **操作流程**：请求 Claude 解释函数及其涉及的模型知识。
- **产出与原文效果**：原文称，通常需要约一小时搜索的问题，可在 10–20 分钟内理解，并将其概括为减少 80% 的研究时间。
- **数字说明**：按“一小时降至 10–20 分钟”计算，时间减少约为 67%–83%；80% 应理解为粗略概括。
- **可迁移做法**：围绕正在阅读的具体函数提问，将知识解释与当前任务结合。

### C13｜将多源文档压缩为排障手册

- **使用团队**：安全工程团队。
- **工作问题**：排障知识分散在多个文档来源，事故期间检索完整知识库效率较低。
- **输入材料**：多个来源的技术文档。
- **操作流程**：汇集文档 → 生成 Markdown 运维手册和故障排查指南 → 将精简文档作为真实生产排障的上下文。
- **产出与原文效果**：形成可复用的排障资料；原文称通常比检索完整知识库更高效，未报告量化结果。
- **可迁移做法**：把常见故障的判断依据和处理步骤沉淀为精简手册，供后续任务复用。

## 七、自动化与跨部门工具

### C14｜分析广告表现并批量生成文案

- **使用团队**：增长营销团队。
- **工作问题**：需要从数百条广告中识别表现不佳者，并快速生成符合字符限制的新版本。
- **输入材料**：包含数百条广告的 CSV 文件、严格的字符数限制。
- **操作流程**：处理 CSV → 识别表现不佳的广告 → 使用两个专门的子代理生成新广告变体 → 满足字符限制。
- **产出与原文效果**：数百条新广告文案；原文称所需时间从数小时缩短至数分钟，未披露广告效果指标和子代理分工细节。
- **可迁移做法**：将结构化数据处理、内容生成和明确的格式约束连接为批处理流程。

### C15｜用 Figma 插件批量生成广告素材

- **使用团队**：增长营销团队。
- **工作问题**：手工替换广告标题和描述、复制素材，耗费大量重复操作时间。
- **输入材料**：Figma 中的设计框架（frames）、待替换的标题和描述。
- **操作流程**：构建 Figma 插件 → 识别 frames → 通过程序替换标题与描述 → 批量生成广告变体。
- **产出与原文效果**：最多 100 个广告变体；原文称原本需要数小时复制粘贴的工作，可达到每批约半秒。
- **范围说明**：该速度对应插件批量替换与生成素材的操作，不能直接视为完整广告制作流程的耗时。
- **可迁移做法**：对于布局固定、内容可替换的任务，制作一次工具，再反复批量执行。

### C16｜制作法律咨询分流工具原型

- **使用团队**：法务团队。
- **工作问题**：员工需要找到适合处理其问题的律师。
- **输入材料**：原文未披露具体需求材料、分流规则或技术实现。
- **操作流程**：借助 Claude Code 制作“phone tree”式咨询分流系统原型，帮助员工找到对应律师。
- **产出与原文效果**：内部咨询分流工具原型；未报告上线情况、使用量或效率数据。
- **可迁移做法**：由熟悉业务规则的人提出需求，先将内部服务流程做成可验证的小型工具原型。
